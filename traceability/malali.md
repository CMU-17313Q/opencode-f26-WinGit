# Traceability: Mohammed Al-Ali (malali)

**Target feature:** the context window meter in the TUI status bar (Issue #5, PR #9). It shows `used / total (xx%)` for the selected model and turns yellow at 80%. The [helper](../packages/tui/src/util/context-usage.ts) works out the count, percentage and warning, and the [prompt status bar](../packages/tui/src/component/prompt/index.tsx) shows it.

## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R5 | After compaction or truncation, the meter updates to the new lower count, shows that compaction happened, and drops the yellow warning if below 80%. | After compaction or truncation, the meter shows the new lower count from the next reply, and the yellow warning goes away if that count is below 80%. | Checkability. "Shows that compaction happened" did not say where or how, so there was no clear pass or fail. The session view already shows a Compaction marker in the message list, so the meter does not need its own label. The part the interviewees cared about (the count drops and the warning clears) stays. |
| R6 | One short message changes the meter only by the tokens that message and its reply add. | Sending a message changes the meter by exactly the difference between the provider-reported totals of the new reply and the previous reply. The meter never adds its own amount on top. | Feasibility. The meter cannot know how many tokens a message "should" add, because tool output and file reads can legitimately add thousands (O-13, O-14). What it can guarantee is that it only reflects what the provider reports and never double counts, which is what the interviewees used to judge whether the number was wrong (O-15). |

## Triage

- **R1** failed on the original code: fast-check shrank it to a 1,000-token window with 799 tokens used. 79.9% was rounded up to 80%, so the meter turned yellow below the line. This also breaks the acceptance case 159,999 / 200,000. **Code bug.** The percentage now rounds down (`Math.floor`), so it never shows 80% or warns before usage really reaches 80%.
- **R5** failed for the same reason (795 / 1,000 shown as 80% and yellow after compaction). Fixed by the same change.
- **R4** failed on the original code: 65 / 1,000 showed 7% instead of 6%. This came from the same rounding. With rounding down, the percentage is now `floor(used × 100 / window)` on every model. The existing unit test that expected 11% for 21,000 / 200,000 (10.5%) was updated to 10%, since it encoded the old rounding.
- **R3** failed on the original code: after an undo, the meter still counted the undone reply (smallest case: an empty conversation plus one reply). **Code bug.** The meter ignored `session.revert`. The helper now takes the revert message ID and ignores that message and everything after it, the same way the session view hides them, and the status bar passes it in.
- **R2** and **R6** passed on the first run.
