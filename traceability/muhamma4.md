## Requirement changes

I kept R1 and R4 as written. R1 is checkable (flag on/off gives the same edit, and the Ctrl-C case already has a test), and R4 is already how the code behaves (20,000-character cap, 10-second timeout, edit is never blocked). I changed five (R2, R3, R5, R7, R8) and dropped one (R6).

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R2 | Running --summary twice on the same unchanged file gives summaries with the same gist (same purpose and main parts); only wording may differ. | Running --summary twice on an unchanged file sends the model an identical request, so the summaries differ at most in wording. | **Can't be checked / not feasible.** A language model's output is not deterministic (the code uses temperature 0.3, not 0), and "same gist" has no automatic test. The user needed stable, trustworthy summaries. What the system controls is the input, so the requirement now fixes the input and leaves the gist as a manual check. |
| R3 | The summary describes the file as it currently is: content still in the file stays in the summary, and content that was removed is not mentioned. | The request sent to the model contains all of the file's current content and none of its removed content. | **Not feasible as stated.** The code cannot force the model to mention or omit specific things. The user needed the summary not to be stale or ignore the file. The build can guarantee the model is given only the current file, so that is now the requirement. |
| R5 | The summary states the file's purpose and main structure in plain terms so a user can compare it against the file, and a failed summary shows a clear warning rather than nothing. | A failed summary shows a clear warning rather than nothing, and a successful one is plain text headed by the file's path so the user can compare it against that file. | **Can't be checked.** "Plain terms" and "main structure" are subjective and depend on the model. The user needed to be able to tell when it was wrong and to never be left guessing. The warning on failure and the path header are checkable. |
| R6 | The summary gives an orientation overview of the file: its purpose, its language, and the main libraries or modules it depends on. | Dropped. | **Not built, and can't be checked.** The feature's instruction to the model asks only for "purpose and structure", so the feature does not do this today. Whether a reply names the right language and libraries depends on the model, so the build can't check it either. Adding it would mean changing the feature, which is outside this project's scope. The interviewees' need (orientation in an unfamiliar file) is partly met by the purpose-and-structure summary. The gap stays documented here. |
| R7 | Across file sizes, the summary keeps the same file-level purpose statement and the detail changes with the file: a longer file's summary names its main components while staying within 3-6 sentences. | Across file sizes, the request asks for the same purpose and 3-6 sentence form. Files over 20,000 characters are summarized from their first 20,000 characters. | **Conflicts with another requirement (R4) and the code.** A 5,000-line file is far over the 20,000-character cap the code applies to keep the summary fast (R4), so the model never sees most of it and cannot name its major components. The user needed the detail to scale with the file within a reasonable wait. The acceptance case now uses a file under the cap, and the 3-6 sentence form is checked on the request. |
| R8 | Every function, class or dependency the summary names exists in the pre-edit file; the summary never invents content. | The summary is built from the file's own content only and is presented as read-only information the user can check. The build does not promise the model never names something that isn't there. | **Not feasible.** No amount of testing can guarantee a language model never invents a name, and the feature has no checker that compares the reply to the file. The user needed to be able to rely on the summary to write a specific prompt. The revision keeps the checkable part (the input is only the file) and leaves invented names as a documented limitation to check by hand. |
